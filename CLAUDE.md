# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## What is nixcage

nixcage is a single-file Bash tool that boots a NixOS microVM for each project and
auto-enters it when you `cd` into the directory. It uses microvm.nix as the VM
backend (cloud-hypervisor on Linux, QEMU on macOS). The primary use case is running
AI coding agents (claude-code, opencode) in full VM-level isolation with
reproducible, Nix-managed environments.

There is no process-level sandboxing (bwrap, Seatbelt). The VM boundary is the only
isolation primitive.

## Repository layout

- `nixcage` -- the entire tool: a single self-contained Bash script (~800 lines).
  All commands and VM lifecycle logic live here.
- `modules/vm-base.nix` -- NixOS module applied to every nixcage VM. Provides
  claude-code, git, nodejs, openssh, the nixcage user, the /workspace virtiofs
  mount, and the secrets injection service.
- `flake.nix` -- flake-parts flake that packages nixcage, exports
  `nixosModules.base`, and defines the dev shell.
- `docs/` -- ADRs and TRACKER.md.

## Development

### Enter the dev shell

```bash
nix develop   # provides bash, jq, shellcheck, bats, openssh
```

### Lint & test

```bash
shellcheck nixcage
bats --recursive tests/
```

There is no build step -- the script runs directly.

### Run locally without installing

```bash
bash nixcage help
bash nixcage init /tmp/test-project
```

## Architecture

The script follows a command-dispatch pattern: `main()` at the bottom dispatches to
`cmd_*` functions.

### Key subsystems

**VM root detection** (`find_vm_root`) -- walks up from `$PWD` looking for
`nixcage.vm.nix`. This file is the presence signal for a nixcage project; it is
also the user's NixOS module.

**Config reader** (`vm_read_config`) -- reads `.nixcage-vm/config` (key=value,
comments allowed) into `VM_*` globals: `VM_SSH_PORT`, `VM_SECRET_VARS`,
`VM_HYPERVISOR`, `VM_SHARE_PROTO`, `VM_NIX_SYSTEM`. This file is gitignored and
regenerated by `nixcage init` because it contains the absolute host path and a
random SSH port.

**SSH helpers** -- `vm_ssh()` wraps ssh with the project-local key and known_hosts.
`vm_wait_for_ssh()` polls until SSH is reachable after boot. `vm_bootstrap_known_hosts()`
runs ssh-keyscan after first boot to avoid interactive host-key prompts.
`vm_inject_secrets()` pipes API key values from host env into `/run/nixcage-secrets`
(tmpfs) inside the VM via SSH; the `nixcage-secrets` systemd service copies that
file to `/etc/profile.d/` so every login shell sources it.

**Init** (`cmd_init`) -- generates all per-project files: `nixcage.vm.nix` (user
config template), `.nixcage-vm/flake.nix` (generated NixOS VM flake), `.nixcage-vm/config`,
`.nixcage-vm/id_ed25519{,.pub}`. Also appends `.nixcage-vm/` to the project root
`.gitignore` (idempotent). The SSH port is selected randomly at init time to avoid
collisions between concurrent projects. Known AI keys (ANTHROPIC_API_KEY,
OPENAI_API_KEY, OPENCODE_API_KEY) are auto-detected from the host environment and
written to `SECRET_VARS=` in the config. `cmd_destroy` reverses the `.gitignore`
edit when removing nixcage files.

**Build** (`cmd_build`) -- runs `nix build .#nixosConfigurations.vm.config.microvm.declaredRunner`
from inside `.nixcage-vm/`. The result symlink points to the hypervisor runner
script. After a successful build, writes a hash of `nixcage.vm.nix` and
`flake.lock` to `.nixcage-vm/build-hash` for stale-build detection.

**Lifecycle** (`cmd_start`, `cmd_stop`) -- start launches the runner in the
background, saves the pid, waits for SSH, bootstraps known_hosts, then injects
secrets. Stop kills the process and removes the pid file.

**Sync** (`cmd_sync`) -- computes the current config hash and compares to
`.nixcage-vm/build-hash`. Rebuilds and restarts if stale, no-ops if current.

**Shell hook** (`cmd_install_hook`, `cmd_vm_hook`) -- `install-hook` appends a
delimited block to `~/.zshrc` or `~/.bashrc` that fires on directory change,
detects `nixcage.vm.nix`, and calls `nixcage shell`. `_vm_hook [zsh|bash]` emits
the hook code to stdout for manual `eval` installation.

### Platform branching

`detect_os()` echoes `"linux"` or `"macos"`; captured at top-level as
`OS="$(detect_os)"`. `cmd_init` branches on `$OS` to choose `hypervisor`
(cloud-hypervisor vs. qemu). Linux uses virtiofs, macOS uses 9p (virtiofsd
is Linux-only). On macOS, `microvm.vmHostPackages` is set to the Darwin nixpkgs
so the runner (qemu) is a macOS-native binary while the guest remains
aarch64-linux. The choice is written into `.nixcage-vm/config` and baked
into the generated flake. At runtime the script is platform-agnostic --
it only manages the VM process and SSH.

### Generated file layout (per project)

```
nixcage.vm.nix          user NixOS module (committed)
.nixcage-vm/
  flake.nix             generated VM flake (gitignored)
  config                SSH port, secret var names, hypervisor (gitignored)
  id_ed25519            SSH private key (gitignored)
  id_ed25519.pub        SSH public key (gitignored)
  known_hosts           populated by ssh-keyscan after first boot (gitignored)
  vm.pid                hypervisor process PID (gitignored)
  vm.log                hypervisor stdout+stderr (gitignored)
  result -> /nix/store  symlink to built VM runner (gitignored)
  build-hash            hash of last successful build inputs (gitignored)
```

Everything in `.nixcage-vm/` is gitignored. Collaborators run `nixcage init` after
cloning to generate their own key pair and config.

## Conventions

- `VM_*` prefix for globals set by `vm_read_config`.
- `vm_*` prefix for SSH/lifecycle helper functions.
- `cmd_*` prefix for top-level command handlers.
- `cmd_build` copies `nixcage.vm.nix` into `.nixcage-vm/` before each build so
  that the generated flake can import it as `./nixcage.vm.nix` within its own
  source tree (Nix pure evaluation forbids escaping the flake directory).
- `nixcage.vm.nix` doubles as both the user config and the project detection signal
  for `find_vm_root` and the shell hook.

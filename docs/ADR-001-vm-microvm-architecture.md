## Context

nixcage sandboxes processes with bwrap (Linux) and sandbox-exec/Seatbelt (macOS).
Both are process-level: the sandboxed tool shares the host kernel. A container
escape or kernel exploit compromises the host. AI coding agents (claude-code,
opencode) are a high-value target -- they hold API keys, have network access, and
execute arbitrary code on the developer's machine.

Beyond security, the process-isolation model has accumulated structural costs: a
custom TOML parser, generated sandbox profiles, four store isolation modes, three
sandbox levels, platform-divergent runners (bwrap vs. sandbox-exec), a direnv
dependency, and XDG state redirection. The result is ~860 lines of policy
enforcement in a Bash script -- fragile, hard to test, and impossible to compose.

The goal: entering a project directory auto-activates a full NixOS microVM. The VM
environment is user-customizable via a standard NixOS module. AI tools are
pre-installed by nixcage and invisible to the user's config. Process isolation is
dropped entirely.

## Decision

nixcage becomes a VM lifecycle manager. Eight interlocking choices:

**1. microvm.nix as the sole execution backend; bwrap and Seatbelt removed.**
microvm.nix (github.com/astro/microvm.nix) takes a `nixosConfiguration` and emits
a runnable store derivation (`declaredRunner`). The VM is the Nix closure --
reproducible, garbage-collected, diffable. bwrap and sandbox-exec are removed. There
is one execution model, one isolation boundary, one behavior across platforms.
The alternative (keeping both) maintains two code paths, two mental models, and the
existing 860 lines of policy logic. Rejected.

**2. Base NixOS module for AI tools; `nixcage.vm.nix` for project additions.**
AI tools (claude-code, opencode) live in `modules/vm-base.nix`, exported as
`nixcage.nixosModules.base`. The user never lists AI tools. Their only file is
`nixcage.vm.nix` -- a plain NixOS module committed to the project repo. Every
concept that lived in `nixcage.toml` maps to a standard NixOS option: packages,
network policy, resource limits, extra mounts, environment variables. The NixOS
module system is composable, typed, and covers options the TOML config could never
reach. `nixcage.toml`, `shell.nix`, and all generated sandbox profiles are removed.

**3. Generated VM flake hidden in `.nixcage-vm/`; project root untouched.**
The NixOS VM flake lives at `.nixcage-vm/flake.nix` -- generated by `nixcage init`,
gitignored, never manually edited. It imports `nixcage.nixosModules.base`,
`microvm.nixosModules.microvm`, and `../nixcage.vm.nix` via relative path. `nix
build` runs from inside `.nixcage-vm/`. The project's own `flake.nix` (if any) is
never read or modified. No merge step, no conflict possible.

**4. Project dir shared via VirtioFS (Linux) / 9p (macOS) at `/workspace`.**
The host project directory mounts into the VM at `/workspace`. The rootfs is
ephemeral; only `/workspace` persists across restarts. VirtioFS is used on Linux
(fast, supported by cloud-hypervisor). 9p is the macOS fallback because `virtiofsd`
is not reliably available as a Darwin package. Extra host paths are declared as
additional `microvm.shares` entries in `nixcage.vm.nix` -- explicit, composable,
no special syntax.

**5. SSH access on an auto-selected port; secrets injected post-boot via SSH pipe.**
`nixcage init` generates an ed25519 key pair (private key gitignored, public key
embedded in the generated VM flake) and selects a random free TCP port. Both are
written to `.nixcage-vm/config` (a key=value file inside the state directory,
gitignored). No hardcoded ports, no manual management, no collisions between
concurrent projects.

Secrets (API keys) are never written to the flake or the Nix store. At init time
the host environment is scanned for known AI keys (ANTHROPIC_API_KEY, OPENAI_API_KEY,
OPENCODE_API_KEY) and their names written to `SECRET_VARS=` in `.nixcage-vm/config`.
After boot, `nixcage start` pushes their values into `/run/nixcage-secrets` (tmpfs,
never flushed to disk) via SSH pipe; a systemd one-shot copies `/run/nixcage-secrets`
to `/etc/profile.d/` so every login shell sources it. QEMU `-fw_cfg` exposes data
at `/sys/firmware/` inside the VM and is not portable to cloud-hypervisor. Rejected.

**6. Shell hook installed via `nixcage install-hook`; direnv dependency dropped.**
A zsh `chpwd` hook (bash `PROMPT_COMMAND` equivalent) fires on directory change,
detects `nixcage.vm.nix` in `$PWD`, and calls `nixcage shell` -- which starts the
VM if not running, then opens an interactive SSH session. `nixcage install-hook`
detects the active shell, checks for an existing installation (idempotent), and
appends a delimited block to `~/.zshrc` or `~/.bashrc`. `--remove` strips it.
direnv is no longer a dependency or a generated file. After a fresh clone the hook
fires on `cd`, finds no `.nixcage-vm/` state directory, and directs the user to run
`nixcage init` before the VM can start.

**7. `nixcage sync` for smart rebuild; stale warning on `nixcage start`.**
`nixcage build` is explicit. Day-to-day, `nixcage sync` hashes the locked flake
inputs and `nixcage.vm.nix`; if either changed since the last build it rebuilds and
restarts the VM, otherwise it is a no-op. `nixcage start` warns (without blocking)
if the build is stale, directing the user to `nixcage sync`.

**8. Hypervisor platform-branched at init time; Lima not used.**
Linux: `cloud-hypervisor` (KVM, ~500ms boot). macOS: `qemu` (~2-3s, TCG or Apple
HVF). Lima adds an external dependency and unnecessary indirection for v1. The
hypervisor choice is written into `.nixcage-vm/config` at init time and is
transparent to the user.

## Consequences

- **~860 lines removed** from the script: `run_linux`, `run_macos`, `parse_config`,
  sandbox profile generation, store mode logic, XDG redirection, `escape_sq`,
  `copy_store_closure`, `setup_local_dirs`, and all Seatbelt helpers. What remains
  is VM lifecycle, SSH management, secret injection, and UX (~600 lines).
- **Single mental model.** One init, one config file, one way in. No sandbox levels,
  no store modes, no platform-divergent behavior.
- **Host `/nix/store` is shared read-only across all VMs** via VirtioFS/9p (handled
  transparently by microvm.nix). Packages declared by multiple projects are built
  once and reused. Subsequent `nixcage build` invocations only build what is not
  already in the host store. VMs cannot write to the store at runtime -- all packages
  must be declared in `nixcage.vm.nix` and built on the host before `nixcage start`.
  This is the correct constraint: it keeps the VM environment reproducible.
- **macOS tools are unavailable inside the VM.** The guest is always Linux/NixOS.
  This is the explicit trade-off for uniform behavior. Users who need macOS-native
  binaries use the host directly.
- **CI use is out of scope.** VM boot latency and hypervisor dependencies make
  nixcage unsuitable for CI pipelines. `nix develop` serves that use case.
- **VM boot latency** (500ms-3s) replaces near-instant process spawn (~100ms). This
  is acceptable because VMs are long-lived per session -- first `cd` starts the VM,
  subsequent connections are fast SSH reconnects (~50ms).
- **`nixcage init` must be re-run after every fresh clone.** `.nixcage-vm/` is
  gitignored; the SSH key pair and port assignment do not survive a clone. This is
  intentional -- secrets and keys are never committed.
- **Updating AI tools** requires `nix flake update nixcage` + `nixcage sync`. More
  deliberate than editing a config file; ensures reproducibility.
- **v0.x compatibility is intentionally broken.** This is a 1.0 rewrite. Existing
  `nixcage.toml` projects, `.envrc` hooks, and `.nixcage/` directories are not
  migrated or detected. No shims, no deprecation warnings. Users re-initialize with
  `nixcage init`.
- **`cloud-hypervisor` port forwarding** via `user` networking needs verification.
  If SLIRP-style forwarding is unsupported, the Linux path switches to vsock-based
  SSH. Implementation-time risk, not a design risk.
